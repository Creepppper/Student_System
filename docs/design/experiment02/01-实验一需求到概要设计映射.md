## 1. 映射规则

- **A 现成基础**：若依已有登录、RBAC、菜单、日志、代码生成等，可直接复用；
- **B 需适配**：在若依基础上扩展账号-业务档案绑定、数据范围、业务审计；
- **C 待新建**：学生业务模块、表、接口和前端页面均未实现；
- **P1**：实验一 P1 扩展，单独设计，不能混入 P0 实现；
- **DR** 是实验一概念数据对象，不是当前物理表；
- 规划路径是命名建议，最终以概要设计评审和 OpenAPI 为准。

## 4. 设计边界

1. **不把 `sys_user` 当学生**：学生档案 `STUDENT` 与账号 `SYS_USER` 分离，通过绑定表/业务账号关联。
2. **不把 `sys_dept` 当行政班**：班级是学年下的业务实体，部门树不是班级树。
3. **不把 `sys_role` 当业务角色**：四类业务角色需要在若依角色/权限上映射，具体“角色名/role_key”待设计。
4. **不把 `sys_oper_log` 当成绩审计**：成绩审计需要前后值、原因、版本、对象多态；操作日志只作系统层。
5. **不把 P1 当 P0**：复核、导入导出、趋势、对比不进入 P0 验收。

## 5. 后端分层建议

```text
Controller（REST/权限）
  -> Service（事务/状态机/权限范围）
    -> Mapper（MyBatis XML/注解）
      -> MariaDB（业务表）
```

- 所有写操作必须 `@Transactional`；
- 状态变更必须校验前置状态和操作人；
- 关键变更同事务写业务审计；
- 列表/详情/统计/导出统一按当前用户和业务范围过滤；
- 接口使用统一 `AjaxResult`/`TableDataInfo`；
- 建议新业务模块 `ruoyi-student`（待评审）而不是把学生实体塞进 `ruoyi-common`。

## 6. 前端映射建议

| 前端层 | 目录（建议） | 说明 |
| --- | --- | --- |
| API | `frontend/src/api/business/` | 按 org/student/exam/score/publication/query/stat/audit 分组 |
| 视图 | `frontend/src/views/business/` | 菜单 component 指向该目录 |
| 路由 | 后端 `sys_menu` 动态下发 | 不硬编码到 constantRoutes |
| 权限 | `business:*` | 与 `system:*` 分开，后端 `@PreAuthorize` 再校验 |
| 状态 | Pinia 页面内/业务 store | 不把成绩数据长期放全局 store |

## 7. 结论

46 项 FR（35 P0 + 11 P1）全部有映射落点；其中 **AUTH 5 项复用/适配**，**其余 P0 与全部 P1 为待新建**。  
本映射不创建任何 Controller、Service、Mapper、表或前端页面。
