# 03 学生业务物理表结构设计

> 设计草稿，未执行、未部署。  
> SQL：`sql-draft/01-p0-schema.sql`、`sql-draft/02-p1-extensions.sql`；字段全表见 `03-完整数据库字段字典.md`。  
> 命名：统一 `stu_` 前缀；`stu_` 表示“学生管理业务域”，不是“只有学生实体”。

## 1. 命名方案比较

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| `stu_*` | 短、与 `sys_*`/`QRTZ_*`/`gen_*` 明显区分；课程示例常用 | 表名读起来都带“学生”，需在文档说明是业务域前缀 | **推荐，全部统一** |
| `biz_*` | 通用、语义中性 | 不能直接看出学生业务；与其他业务扩展区分弱 | 不推荐 |
| `edu_*` | 教育域语义更准确 | 课程/团队约定不明确；与现有命名风格不一致 | 备选 |

**决策：P0/P1 全部使用 `stu_`；不混用 `biz_`/`edu_`/无前缀。**

## 4. 主键/类型规则

- 所有**新建业务主表**：`id INT NOT NULL AUTO_INCREMENT PRIMARY KEY`；
- 学号/工号/考试编码是业务唯一键（`VARCHAR` + UK），**不是自增主键**；
- `sys_user.user_id` 是 `BIGINT`，`stu_account_binding.user_id` 必须 `BIGINT`；不修改若依原表；
- `stu_*` 外键列使用 `INT`（引用 `stu_*.id`）；`sys_user` 逻辑关联用 `BIGINT`；
- 成绩/满分/线统一 `DECIMAL(6,1)`，不用 FLOAT/DOUBLE；
- 状态/代码使用 `VARCHAR` + Service 代码常量/`CHECK`；不把数据库当唯一状态机；
- 审计快照 `LONGTEXT`（应用 JSON），不用数据库专有 JSON 作为跨库硬依赖。

## 5. 关键字段设计

### 5.1 成绩三态

`stu_score`：

```text
score_status = SCORE_NORMAL       -> score_value NOT NULL, 0.0..满分, 0.5 步长
score_status = SCORE_ABSENT       -> score_value NULL（显示“缺考”）
score_status = SCORE_NOT_ENTERED  -> score_value NULL（阻止提交）
```

- 真实 0 分：`SCORE_NORMAL + 0.0`，不是 `ABSENT/NOT_ENTERED`；
- `CHECK` 负责状态/空值/非负/0.5 步长/防御性上限；
- **精确满分**由 Service 按任务快照/考试科目校验（跨表 CHECK 不可用）；
- 缺考/未录入不进入有效人数/总分分母；完整总分才排名。

### 5.2 任务唯一与快照

`stu_score_task`：

- 唯一 `(exam_id,class_id,subject_id)`；
- `first_owner_teacher_id` 是创建时班主任快照；
- `full_mark_snapshot/pass_line_snapshot/excellent_line_snapshot` 保存任务生成时的线；
- `roster_version` 保存生成时花名册版本；
- 提交/审核/退回不删除任务，历史保留。

### 5.3 发布三表

```text
stu_publication                当前状态：PUB_UNPUBLISHED/PUBLISHED/WITHDRAWN + current_version_id
  └── stu_publication_version  不可变版本头：version_no、snapshot_at、based_on、hash
        └── stu_publication_version_detail  不可变成绩明细：version×student×subject
```

- 当前发布唯一 `(exam_id,class_id)`；
- 版本唯一 `(publication_id,version_no)`；
- 撤回只改当前状态，不删版本；
- 重新发布版本 +1；
- 更正保持 `PUB_PUBLISHED`，新增版本，不覆盖历史；
- 版本明细不引用可变 `stu_score`，避免后续更正污染历史。

### 5.4 账号绑定

`stu_account_binding`：

- `user_id BIGINT`；`profile_type` `STUDENT`/`HEAD_TEACHER`；
- `student_id`/`head_teacher_id` 二选一，`CHECK` 保证类型匹配；
- `active_user_key`、`active_profile_key` 生成列 + UNIQUE；
- `binding_status=ACTIVE/REVOKED`，历史撤销保留；
- 不建 `sys_user` 物理 FK；服务层校验账号存在/未停用/类型匹配；
- 一个档案最多一个有效账号，一个账号最多一个有效绑定（不论类型）。

## 6. 总分与排名策略

**推荐 P0：不单独持久化总分/排名表。**

- 总分由当前发布版本的 `stu_publication_version_detail` 按学生汇总（完整科目）；
- 排名在查询时按同一考试×班级、同一口径计算（1,2,2,4）；
- 缺考/未录入不伪造 0；缺考不进入有效人数/总分分母；
- 更正/撤回/重发后，当前版本变化，查询自动使用新版本；
- 可对只读结果做短 TTL 缓存，但**缓存不是真值**，版本变化必须失效；
- 若未来性能需要，增加派生汇总表也必须以 publication_version_id 为版本键，不能覆盖历史。

> 不在本阶段建汇总表；`stu_publication_version_detail` 是可回溯的事实快照。

## 8. 兼容性/迁移风险

| 项 | 说明 |
| --- | --- |
| MySQL 8 / MariaDB 11.8 | 生成列、CHECK、utf8mb4、InnoDB 基本兼容；仍需在测试库实跑 DDL |
| JSON | 审计前后值用 `LONGTEXT`，应用负责 JSON；避免 MariaDB JSON 别名差异 |
| 时间区间 | 普通 UNIQUE 不能表达不重叠；Service 事务 + 行锁 + 索引 + 生成列共同保证 |
| 循环 FK | `publication.current_version_id` 在表创建后 `ALTER` 补加；也可降级逻辑关联，需评审 |
| 删除 | 全部 `RESTRICT`；历史/成绩/发布禁止级联删除 |
| 原表 | 不修改 `sys_*`、`QRTZ_*`、`gen_*`；不动主键类型 |
| 迁移 | 草稿不能直接上线；需备份、评审、测试库演练、回滚脚本与数据校验 |
