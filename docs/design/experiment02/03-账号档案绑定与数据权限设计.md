# 03 账号—档案绑定与数据权限设计

> 本文是设计，不是已实现代码。账号仍使用若依 `sys_user`；学生/班主任档案是新建业务表。  
> 关键事实：`sys_user.user_id` 为 **BIGINT**；新建业务主键为 **INT**，绑定表 `user_id` 必须 BIGINT。

## 1. 绑定模型

```text
sys_user (A, BIGINT user_id)
  └── stu_account_binding (new, user_id BIGINT)
        ├── STUDENT       -> stu_student.id (INT)
        └── HEAD_TEACHER  -> stu_head_teacher.id (INT)
```

`stu_account_binding` 关键字段：

- `user_id BIGINT NOT NULL`
- `profile_type VARCHAR(20)`：`STUDENT` / `HEAD_TEACHER`
- `student_id INT NULL`、`head_teacher_id INT NULL`
- `binding_status VARCHAR(16)`：`ACTIVE` / `REVOKED`
- `effective_from`/`effective_to`
- 生成列 `active_user_key`、`active_profile_key` + UNIQUE

约束：

- 一个档案最多一个有效账号；
- 一个账号最多一个有效绑定（不分学生/班主任类型）；
- 类型与档案字段必须匹配（`CHECK`）；
- 撤销保留历史，不物理删除；
- `user_id` **不建物理 FK** 到 `sys_user`：若依表可能软删除/迁移；服务层强校验账号存在、状态正常、类型匹配；
- 学生/班主任档案 ID 可以建物理 FK（`RESTRICT`）。

## 2. 为什么不能只看 `sys_user`

- `sys_user` 是登录账号，不是学生档案；
- 学生可以没有账号，或账号停用但档案/历史成绩保留；
- 班主任档案与账号分离，换人/停用可追溯；
- 一个账号不能同时绑定学生和班主任（`CHECK` + 服务层）；
- 一个学生档案不能同时绑定多个有效账号；
- 历史停用账号不能借旧 Token/旧绑定看他人的成绩；
- 系统管理员可以管理账号，但**不能凭管理员身份查看成绩明细**。

## 3. 四类角色与数据范围

| 角色 | 范围 | 允许 | 禁止 |
| --- | --- | --- | --- |
| 系统管理员 | 系统账号/绑定/系统配置 | 账号、绑定、审计脱敏、系统参数 | 成绩明细、审核/发布/更正；不得以 `admin` 绕过 |
| 教务管理员 | `SCOPE_ALL` | 组织、考试、审核、发布、撤回、受控更正、全校统计 | 代替班主任录入；自审；改历史版本 |
| 班主任 | `SCOPE_CLASS` | 当前有效任职班级的全科任务、录入、提交/重提、本班统计 | 跨班；改已发布；审核自己的任务；看其他班 |
| 学生 | `SCOPE_SELF` | 本人已发布成绩/排名/复核申请（P1） | 他人；未发布/已撤回；成绩明细导出 |

**不恢复任课教师/任教关系。**

## 4. 数据范围实现顺序

```text
1. JWT 认证（SecurityConfig / JwtAuthenticationTokenFilter）
2. @PreAuthorize 功能权限（business:*）
3. Service 读取当前登录 user_id + 有效绑定
4. 按角色推导业务范围：
   - 系统管理员：拒绝成绩明细
   - 教务：SCOPE_ALL
   - 班主任：当前有效任职班级集合
   - 学生：绑定 student_id + 发布状态
5. 查询条件必须包含范围（不能只在前端/Controller 过滤）
6. 返回前再次校验对象归属/发布状态
```

`@DataScope` 只解决若依部门/用户数据权限，**不能替代本班/本人**。

## 5. 若依超级管理员的绕过风险

源码事实：

- `SysPermissionService.getRolePermission()`：`user.isAdmin()` 时加入 `SUPER_ADMIN`；
- `getMenuPermission()`：`user.isAdmin()` 时加入 `ALL_PERMISSION`；
- `TokenService` 刷新权限时对 admin 跳过角色判断；
- 因此仅靠 `@PreAuthorize("@ss.hasPermi('business:score:view')")` **不能保证 admin 看不到成绩**：admin 可能拥有全部权限。

**设计结论：**

- 在业务 Service 的**最前面**增加显式 `BusinessAccessGuard`：
  - 当前账号是系统管理员 → 对成绩明细/成绩导出/成绩查询接口直接拒绝（或只返回脱敏元数据）；
  - 不把“拒绝”只放在前端菜单或按钮；
  - 不依赖 `@DataScope`；
  - 统一错误码 `BUSINESS_SENSITIVE_FORBIDDEN`；
  - 记录安全审计（不记录成绩内容）。
- 审核/发布/更正服务还要校验操作人不是提交人，即使 admin 也不能绕过。
- 这是**规划中的 Service 组件**，当前未实现。

## 6. 班主任范围

- 只读取 `stu_head_teacher_assignment` 中 `head_teacher_id=当前绑定` 且 `is_current=1`、`effective_to IS NULL` 的班级；
- 对任务再校验 `task.class_id ∈ 当前有效班级`；
- 任务 `first_owner_teacher_id` 只用于快照/审计，不作为永久授权；
- 换班后旧任务自动变为只读（教务可处理）；新任务只给新班主任；
- 多班班主任按班级分别查询，不做跨班混合排名（推荐 A，待评审）。

## 7. 学生范围

- 通过有效 `stu_account_binding` 得到 `student_id`；
- 只查 `stu_publication` 当前 `PUB_PUBLISHED` 的 `publication_version_detail`；
- 不查 `stu_score` 可变表；
- 撤回后当前状态 `PUB_WITHDRAWN` → 不可见；
- 不能通过改 URL/参数查他人；Service 不接受前端传入的 `student_id` 作为授权依据；
- 复核申请 P1 只对本人已发布成绩，且受时限/活跃唯一约束。

## 8. 停用/撤销

| 场景 | 处理 |
| --- | --- |
| 账号停用 | `sys_user.status` 校验失败；已有 Token 由若依登录态/在线用户机制处理；绑定不删除 |
| 绑定撤销 | `binding_status=REVOKED`，`effective_to` 填写；历史保留 |
| 学生毕业 | 学生 `GRADUATED`；不再新建任务；历史成绩保留 |
| 班主任离任 | 关闭任职记录；旧任务保留第一责任人快照；新任务给新班主任 |
| 系统管理员查看 | 脱敏审计/账号元数据；成绩明细拒绝 |

## 9. 事务与并发

- 绑定/解绑：同一事务锁 `user_id`/`student_id`/`head_teacher_id`，校验唯一，再插入/关闭；
- 生成列唯一键是最后防线；冲突时返回可读错误，不静默覆盖；
- 学生转班/班主任换班：同一事务关闭旧关系 + 插入新关系；
- 不能只依赖普通 UNIQUE 表达时间区间；使用 `SELECT ... FOR UPDATE` 或等价行锁 + 校验；
- 不修改 `sys_user` 表结构/主键类型；不删除若依原生账号。
