## 2. 统一角色与业务边界

| 角色 | 职责 | 不允许 |
| --- | --- | --- |
| 系统管理员 | 账号/角色/菜单/按钮权限、审计查询 | 默认查看成绩明细；代替教务审核/发布 |
| 教务管理员 | 基础资料、考试配置、审核/发布/撤回/更正、全校统计、P1 最终确认 | 代替班主任录入；审核自己提交的任务 |
| 班主任 | 本班全部适用科目的录入/暂存/提交；本班统计；P1 受理/核查 | 跨班录入；自行撤回已提交任务；最终确认/更正 |
| 学生 | 本人已发布成绩查询；P1 复核申请/查看 | 查看他人/未发布成绩；直接改分 |

边界外不画数据库、缓存、若依框架组件为业务 Actor。**任课教师不是角色，任教关系不是实体/关联。**

## 4. 模型决策

1. **FIG-03 采用“业务目标级总览 + 角色子图”**：总览 7 个业务目标；03A～03D 按角色展开登录、资料、考试、成绩、统计、审计、P1；避免 19 个用例挤在一张图。
2. **FIG-05 采用“核心总览 + 4 个局部类图”**：总览 9 个核心类；05A 组织/人员/任职/账号；05B 考试/任务/成绩；05C 发布/审计；05D P1 复核。总览中的“当前归属/当前任职”是简化关联，历史化关联在 05A。
3. **FIG-06 拆为三个独立状态机**：考试/成绩任务/班级发布生命周期各自独立；`TASK_APPROVED` 与 `PUB_PUBLISHED` 不混用；三图共享状态字典但互不替代。
4. **FIG-07 主链路 + 07A 异常分支**：主图保留数据非法、未录入、审核退回、发布、撤回；07A 展开异常处理、重提和不可见性，避免主图无限交叉。
5. **FIG-08 P1 单独时序**：学生→系统→班主任受理/核查→教务最终确认/更正；P1 明确不进入 P0 退出条件，不设任课教师核查。
