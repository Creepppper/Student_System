## 1. 系统定位

### 1.1 名称与定位

【已采用】系统暂定名称为 **高中学生信息与成绩管理系统**。

【已采用】系统面向 **单所高中**，围绕学年、学期、年级、班级、学生、教师、科目、考试、成绩和成绩发布开展管理。

【工作基线】用一句话定义：

> 面向单所高中的教务、教师和学生，提供“基础资料 → 考试配置 → 成绩录入 → 审核发布 → 学生查询 → 变更留痕”的闭环管理，并在 P1 增加成绩复核、导入导出和趋势分析。

### 1.2 明确的定位边界

【已采用】不得把系统扩展为：

- 大学选课、学分、GPA、学位或正式成绩单系统；
- 完整智慧校园 ERP（缴费、宿舍、图书馆、排课、门禁、资产等）；
- 多学校 SaaS 或多租户平台；
- 高考预测、志愿推荐或 AI 分析平台。

【工作基线】系统定位为**课程项目可演示、可验收的单校业务系统**，优先保证主链路完整、权限边界清晰、成绩口径可验证，而不是追求模块数量。

## 2. 业务背景与问题假设

> 以下问题是根据课程场景和调研形成的**业务假设**，尚未经过真实校方访谈；在正式 SRS 中应标注来源，不能写成已核实事实。

【建议】目标学校可能面临以下问题：

1. 成绩分散在教师个人表格中，科目、满分、缺考和总分口径不统一；
2. 任课教师、班主任、教务之间的成绩查看和修改权限缺少系统约束；
3. 成绩提交后缺少审核与发布控制，学生可能提前看到未定稿数据；
4. 成绩修改缺少前后值、操作人、时间和原因记录，出现争议时难以追溯；
5. 学生只能通过口头或张贴获取成绩，无法自主查询本人历史成绩；
6. 成绩复核流程依赖线下沟通，申请、受理、核查和更正缺少统一记录。

这些问题只用于说明系统价值，不作为需求证据。正式 SRS 需要为每条需求标注“来源”（课程场景、用户决策、调研结论或待访谈）。

## 3. 系统目标

| 目标 ID | 目标 | 可观察的成功条件 |
| --- | --- | --- |
| `G-01` | 建立一条完整可演示的成绩主链路 | 能从基础资料配置走到学生查询已发布成绩，全程不依赖手工改库 |
| `G-02` | 统一成绩口径 | 满分、及格/优秀线、总分、排名、缺考和未录入在所有页面和统计中口径一致 |
| `G-03` | 建立角色与数据双重边界 | 学生只看本人；教师只看授权班级×科目；班主任只看本班；教务看全校 |
| `G-04` | 控制成绩审核与发布 | 未经审核的成绩不能发布；未发布的成绩学生不可见；发布和撤回均有记录 |
| `G-05` | 保证成绩变更可追溯 | 关键成绩变更能还原操作人、时间、原因、修改前后值和版本 |
| `G-06` | 复用若依基础能力 | 登录、JWT、角色、菜单、按钮权限、字典和操作日志不重复造轮子 |
| `G-07` | 为 P1 留出稳定扩展点 | 复核、导入、趋势和对比不推翻 P0 的实体、状态和权限模型 |

【建议】`G-01` 至 `G-07` 是基线级目标，不替代后续可测量的非功能需求（NFR）。性能、并发、可用性等指标在 SRS 阶段结合课程验收环境另行确认，本阶段不承诺 7×24、容灾或未压测的数值。

### 4.2 范围外

| 范围外内容 | 处理 | 理由 |
| --- | --- | --- |
| 高考成绩预测、志愿推荐 | 排除 | 需要可信外部数据、算法解释和合规说明，超出课程项目 |
| 大学选课、学分、GPA、学位、正式成绩单 | 排除 | 与固定行政班高中场景不符 |
| 缴费、宿舍、图书馆、排课、门禁、资产 | 排除 | 属于完整校园 ERP，不是本系统问题 |
| 家长门户、短信/微信推送 | P2，暂不规划 | 涉及监护关系、隐私授权和外部服务，首期不纳入 |
| 多学校 SaaS、多租户 | 排除 | 本系统明确单校部署 |
| 在线考试、题库、阅卷、考场座位 | 排除 | 与“成绩管理”主链路无直接关系 |
| 通用工作流引擎、复杂会签 | 排除 | 首期只做一级教务审核，不引入通用流程平台 |
| 移动原生 App | 排除 | 首期以桌面浏览器为主；响应式适配不等于原生 App |

### 4.3 外部实体与系统边界

【工作基线】业务上下文中的外部实体只有：

- 学生；
- 任课教师；
- 班主任；
- 教务管理员；
- 系统管理员。

【已采用】数据库、Redis/Valkey、Controller、Service 等是系统内部技术构件，**不得作为业务 Actor**。

【工作基线】首期不接入校外系统、支付、短信、统一身份认证或教务大数据平台；若后续需要，必须单独评审接口、隐私和失败降级。

## 8. 术语

> 术语在 SRS、DFD、ER、UML、原型和代码中必须保持一致。状态名以 `04-核心业务规则.md` 的状态字典为准，本文件不另造状态名。

| 术语 | 定义 | 不使用的近义词/说明 |
| --- | --- | --- |
| 学年 | 如 `2026-2027` 的教学年度 | 不把“学期”混称为学年 |
| 学期 | 学年内的第一学期或第二学期 | 考试和任教关系必须挂到学期 |
| 年级 | 高一、高二、高三的年级层次 | 不把“班级”当年级 |
| 班级 | 某一学年、某一年级下的行政班，如“2026-2027 学年高一(1)班” | 一个班级只属于一个学年 |
| 学生 | 业务档案中的学生，不等同于若依登录账号 | 学生档案与账号分离 |
| 教师 | 业务档案中的教师，不等同于若依登录账号 | 教师可同时是任课教师和班主任 |
| 科目 | 语文、数学、英语、物理、化学、生物等可配置科目 | 不把“考试科目”当科目主数据 |
| 任教关系 | 某学年某学期，某教师教某班级某科目 | 不是“班主任关系” |
| 班主任 | 某一班级在本学年的负责教师，首期每班一名 | 班主任不等于该班所有科目的任课教师 |
| 考试 | 一次有类型、学期、范围、科目和状态的教学测验 | 不把“考试科目”当考试 |
| 考试科目 | 某次考试中的某科目配置，含满分、及格线、优秀线 | 满分以考试科目配置为准 |
| 成绩 | 某学生某次考试某科目的结果，由“状态 + 数值”组成 | 缺考不是 0 分 |
| 成绩精度 | 成绩、满分、及格线、优秀线统一采用 0.5 分步长、一位小数；计算和比较使用定点十进制 | 禁止二进制浮点直接相等比较；不得出现 0.499999 之类的显示 |
| 成绩录入任务 | 考试×班级×科目的录入/提交单元 | 不把单个分数字段当提交单元 |
| 班级成绩发布 | 考试×班级的发布单元 | 不把“任务已通过”直接等同于“已发布” |
| 成绩复核 | P1 中学生对本人已发布成绩提出的复查申请及处理过程 | P0 的教务更正不叫复核 |
| 业务变更记录 | 对成绩、任务、发布、范围、归属等关键变更的审计记录 | 不等同于若依通用接口操作日志 |

## 9. 已采用、建议与待小组确认汇总

### 9.1 已采用（工作基线）

- 系统暂定名称：高中学生信息与成绩管理系统；
- 面向单所高中；
- 首期五类业务角色：系统管理员、教务管理员、任课教师、班主任、学生；
- 不扩展为大学选课系统、完整智慧校园 ERP、多校 SaaS；
- P0/P1/P2 的分期框架；
- 25 项 D 决策按用户本次方案采用；D-019 为课程模拟假设，待小组确认；
- 本阶段只产出需求文档，不修改 Java、Vue 或数据库。

### 9.2 已纳入工作基线的方案

- 引入“学期”作为考试和任教关系的时间维度；
- 学生班级归属按学年保留历史，不用单一 `class_id` 覆盖；
- 成绩提交/审核按“考试×班级×科目”，发布按“考试×班级”；
- 成绩状态与数值分离，缺考/未录入不记为 0；
- 总分只对完整成绩计算，班级排名采用竞争排名；
- 班主任默认只读本班汇总并协助复核，不默认拥有全科改分权；
- 系统管理员不参与教务审批，内置超级管理员只用于初始化/应急；
- 分数精度采用 0.5 分步长、一位小数，计算与比较使用定点十进制；
- P0 只做单场考试的基础统计，趋势和班级对比放 P1。

### 9.3 已采用的关键决策

| 决策 ID | 问题 | 采用结论 |
| --- | --- | --- |
| `D-003` | 成绩录入/修改主体 | 任课教师按任教关系；班主任只读 |
| `D-004` | 提交/审核/发布粒度 | 提交/审核按考试×班级×科目；发布按考试×班级 |
