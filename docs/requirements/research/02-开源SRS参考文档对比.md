## 3. 分仓库分析

### 3.1 R1：CampusCare

原文事实：文档面向高校院系，包含学生信息、班级、考勤、奖惩和成绩五个模块；管理员、辅导员、学生三类角色；用 CRUD 表格列出操作，文本列出核心字段和数据关系；NFR 给出查询、批量导入、并发、JWT、bcrypt、日志、脱敏、可用性和浏览器支持；最后给出 8 周迭代计划。仓库没有 DFD、ER、UML 或需求追踪材料。

本项目判断：其“学生唯一编号、班级无学生才能删除、成绩修改留痕、分数段统计、软删除”的粒度适合作为业务规则启发。辅导员、奖惩、大学院系／课程／学期等概念不能直接搬到高中场景。JWT 有效期、10 万条 1 秒、99.5% 等参数只能作为参考，必须由本项目环境和测试方案重新确认。

### 3.2 R2：ISMS Requirements Analysis

原文事实：PDF 按 9 个任务组织：现状与目标、利益相关者、功能需求、非功能需求、用例、类图、顺序图、假设／约束／风险、范围。它覆盖国际学校的学生、教师、班级、考勤、考试与成绩、收费、家长／学生门户、报表、RBAC、通知、审计和双语；提供 14 个用例的主流程、备选和后置条件；包含总用例图、较大的领域类图和多个顺序图；明确列出 1.0 范围内外功能。

本项目判断：最值得借鉴的是“先写业务问题和成功标准”“显式列出 in-scope/out-of-scope”“用例包含异常路径”。收费、支付网关、短信、双语、家长通信、排课冲突与完整考勤会显著扩大课程项目范围；GPA 也不是普通高中成绩管理的自然概念。其“100% 成绩准确”等 NFR 无法按字面验收，应改成计算规则测试通过率、事务一致性和错误检测规则。

### 3.3 R3：Academic MIS Documentation

原文事实：项目明确是分析文档而非应用，聚焦 Enrollment、Attendance、Grading 三个过程；包含 0 层 DFD、1 层 DFD、6 实体 ER 图、流程叙述、SQL 和 `FR-1` 至 `FR-4` 的功能规格；追踪矩阵把 FR 映射到 DFD 过程和 ER 实体。其核心建模选择是成绩和考勤关联 `enrollment_id`，并以 75% 出勤率作为考试资格门槛。

本项目判断：这是结构化分析和轻量追踪最好的参考，尤其适合学习“图、叙述、实体、需求编号互相一致”。但课程注册、学分、学期选课、内外部考试 40/60、GPA 和出勤资格属于大学场景。高中系统应改成“学生—班级归属”“考试—科目—成绩”，不要引入没有业务依据的 Enrollment 或 Credits。

### 3.4 R4：SoftwareEngineering-2024

原文事实：40 页 PDF 是课程型作业，先介绍 CASE/UML，再给问题陈述和 SRS，随后按实验编号展示 DFD、ERD、用例、活动、类、顺序、状态、组件、协作和部署图。业务包括学生注册、课程、考勤和结果管理，角色有学生、教师、教务管理员、系统管理员。

本项目判断：它适合核对“某类图长什么样”及课程交付顺序，不适合作为需求正文模板。文档混合了分析、设计和部署，图很多但追踪和验收较弱，部分需求仍停留在概述层。新 SRS 不应为了图的数量复制其组件图、协作图和部署图；这些更适合设计阶段。

### 3.5 R5：SchoolOS-old

原文事实：主 SRS 定义 24 个企业级模块、多租户、Web/Mobile、流程引擎和审计；要求每项功能需求包含 ID、目标、Actor、前置、触发、主／备选流、后置、业务规则、验证、安全、审计、数据实体、验收和追踪。单项“学生注册”“成绩录入与审核”“结果发布”等文档有生命周期、依赖、验收标准和 ADR 追踪。仓库同时包含大量未完成的 0 字节占位文档；未发现 DFD、ER 或 UML 图资产。

本项目判断：需求编号、验收条件、状态、依赖和追踪机制值得缩减后采用。多租户、招生、收费、家长、HR、考勤、访客、门禁、交通、库存、工作流引擎、证书、GPA/CGPA、区块链和 AI 都远超本课程项目。其验收标准常只有“成功生成／完成”，仍需改成可观察条件和具体业务规则。

## 4. 高中场景的适用与不适用内容

### 4.1 适合吸收为本项目建议

- 学生唯一学号、年级—班级组织、教师与任教科目／班级关系。
- 考试、考试科目、成绩、录入批次、审核与发布状态。
- 学生只能查看本人已发布成绩；教师只能处理授权班级／科目；管理员控制发布。
- 成绩修改原因、修改前后值、操作者和时间的审计记录。
- 需求 ID、优先级、来源、验收条件和追踪矩阵。
- 用环境图／DFD 固定边界，用概念模型／ER 固定术语和关系。
- 将范围内、范围外、未来候选功能明确分开。

### 4.2 不应直接带入的大学或企业场景

- 学生自由选课、课程注册、课程容量、退选、学分、GPA/CGPA、学位与成绩单。
- 75% 出勤率决定考试资格、内外部考核 40/60、补考／重修等规则，除非老师明确提出。
- 辅导员、学院、Exam Cell 等大学组织角色。
- 多租户 SaaS、支付、工资、交通、门禁、访客、宿舍、图书馆、库存、工作流引擎。
- AI 成绩预测、志愿推荐、区块链证书、政府平台或短信网关集成。

## 6. 综合结论

建议组合使用而非照搬：

- 章节骨架与质量检查以课程课件为准。
- 用例规约借鉴 R2 的清晰主／备选流，但补上编号、业务规则和验收条件。
- DFD、ER 与追踪矩阵借鉴 R3 的小而一致的做法。
- 需求 ID、状态和追踪字段借鉴 R5，但删去企业级繁复字段。
- R1 用于校验常见 CRUD 与审计规则；R4 仅用于认识图种，不作为“图越多越好”的依据。
