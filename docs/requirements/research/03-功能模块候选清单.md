# 功能模块候选清单

> 状态：候选范围，尚未形成需求基线。  
> “当前基础”指若依已有能力；“业务模块”均尚未开发。

## 1. 范围原则

1. 目标是高中学生信息与成绩管理，不做大学选课／学分系统，也不做完整校园 ERP。
2. 优先形成一条完整可演示的主链路：基础数据 → 建立考试 → 录入成绩 → 审核发布 → 学生查询 → 复核留痕。
3. 用户、角色、菜单、按钮权限、部门／组织、字典、登录日志和操作日志优先复用若依；学生档案与系统登录账号保持概念分离。
4. 所有成绩业务先定义可验证规则，再设计表和页面。
5. 统计只做可解释的基础汇总，不做预测、推荐或复杂数据仓库。

## 2. 建议角色

| 角色 | 建议职责 | 数据范围 |
| --- | --- | --- |
| 系统管理员 | 账号、角色、菜单、字典、系统配置 | 全系统管理，但原则上不替代教务审批 |
| 教务管理员 | 年级班级、学生教师科目、考试、审核发布 | 全校或授权年级 |
| 任课教师 | 录入／提交本人任教班级和科目的成绩，处理复核 | 授权的班级 × 科目 × 考试 |
| 班主任 | 查看本班成绩汇总、协助复核；是否能改全科成绩待确认 | 本班 |
| 学生 | 查询本人已发布成绩、发起和查看复核 | 仅本人 |

不建议把数据库作为 Actor。家长角色本期默认不纳入，避免未成年人账户绑定和家校授权规则扩大范围。

| 暂缓 | 家长门户／通知 | 家长查分、站内或短信通知 | 需新增绑定和通知机制 | 隐私、授权、外部服务均未确认 |
| 排除 | 高考预测／志愿推荐 | 预测分数、推荐院校 | 无 | 需要可信数据、算法、解释与合规，不适合当前实验 |
| 排除 | 选课／学分／GPA | 大学式课程注册与绩点 | 无 | 与固定行政班高中场景不符 |

## 4. 推荐的最小可交付范围

### 4.1 第一优先级闭环

1. 管理员配置学年、年级、班级、科目、教师任教关系和学生档案。
2. 教务创建考试并配置参与班级、科目及满分。
3. 任课教师录入、暂存、校验并提交授权范围内的成绩。
4. 教务审核；有问题则退回，有效则发布。
5. 学生只能查询本人且已发布的成绩。
6. 所有关键提交、退回、发布和改分动作留痕。

这个闭环覆盖项目标题中的“学生信息”和“成绩管理”，也能充分展示若依权限、代码生成、前后端分离与数据库设计。

### 4.2 第二优先级

- 学生发起单科复核，处理人给出结论；确需改分时形成新版本或业务变更记录。
- 班级／科目的平均分、最高分、最低分、分数段和个人趋势。
- 在核心流程稳定后增加 Excel 导入预检，而不是直接覆盖已有成绩。

## 5. 当前建议中可能过于复杂的部分

### 成绩审核与发布

合理但复杂。至少涉及草稿、已提交、已退回、已发布等状态，以及谁能转换状态、发布粒度是整场考试还是“考试 × 班级”、发布后如何修正。建议保留，但先做单级教务审核，不做多级会签和通用工作流引擎。

### 成绩复核

业务价值高，但会把申请状态、处理时限、角色分工、成绩版本和通知串在一起。建议作为 P1，只实现站内状态查询；不接短信，不把线下查卷过程全部数字化。

### 统计与排名

基础统计可行；跨年级标准化、加权总评、赋分、预测和复杂排名不可行。第一版只支持同一次考试、同一班级／科目、相同满分口径。排名并列策略必须先确认。

### 教师与科目

“教师档案”本身简单，“某学年某教师教哪个班哪门科目”才是成绩录入授权的关键。若把班主任等同所有科目教师会产生越权，必须建立明确任教关系。

## 6. 粗略实现分期

| 里程碑 | 内容 | 验收重点 |
| --- | --- | --- |
| M1 基础资料 | 年级、班级、科目、学生、教师、任教关系 | 唯一性、历史归属、数据权限 |

| M3 复核与统计 | 复核、变更历史、基础统计 | 可追溯、统计口径、异常路径 |
| M4 完善 | Excel 导入、性能与可用性优化 | 预检、回滚、并发与容量 |

## 7. 结论

用户提出的十个核心模块总体合理，但建议把“成绩审核发布”和“成绩复核”拆成独立状态流程，把“基础统计”严格限于可验证指标，并将 Excel、家长端、预测推荐放到核心闭环之后。现阶段不应把任何候选模块写成已实现功能。
