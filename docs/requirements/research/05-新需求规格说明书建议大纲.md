# 新需求规格说明书建议大纲

> 状态：建议目录，不是正式 SRS。经老师要求和组内范围评审后再据此写正文。

## 1. 推荐结构

### 封面与文档控制

- 项目名称、文档名称、版本、状态、编写／评审人员、日期。
- 修订记录。
- 审批／评审记录。
- 目录、图目录、表目录。

### 1 导言

1.1 编写目的  
1.2 项目范围  
1.3 预期读者与阅读建议  
1.4 文档约定与需求编号规则  
1.5 缩写与术语  
1.6 引用标准与参考资料

### 2 综合描述

2.1 项目来源与业务背景  
2.2 现状问题  
2.3 系统目标与成功标准  
2.4 产品边界与系统上下文  
2.5 用户角色、特征与数据范围  
2.6 产品功能概览与优先级  
2.7 运行环境  
2.8 约束、假设与依赖  
2.9 范围内／范围外／未来候选功能

### 3 业务模型与数据需求

3.1 业务术语与核心概念  
3.2 业务流程概览  
3.3 结构化分析：环境图和 1 层 DFD  
3.4 领域概念模型  
3.5 数据实体、关系与主要约束  
3.6 数据字典  
3.7 数据保留、隐私与审计要求

### 4 功能需求

4.1 身份、角色与权限  
4.2 年级与班级管理  
4.3 学生信息管理  
4.4 教师、科目与任教关系  
4.5 考试管理  
4.6 成绩录入与提交  
4.7 成绩审核与发布  
4.8 学生成绩查询  
4.9 成绩复核  
4.10 基础统计  
4.11 操作与业务变更记录

每节先列编号功能需求，再给关键用例规约和业务规则。不能只写“增删改查”，要说明谁、在什么条件下、对哪些数据、得到什么可观察结果。

### 5 外部接口需求

5.1 用户界面与原型引用  
5.2 浏览器与终端接口  
5.3 软件接口（若依身份权限、MariaDB/MySQL、Valkey/Redis）  
5.4 通信接口  
5.5 导入导出接口（若纳入范围）

这里描述外部约束和交互，不提前固定 Controller URL、DTO 或表结构；具体 OpenAPI 属于设计／实现文档。

### 6 非功能需求

6.1 性能与容量  
6.2 安全与隐私  
6.3 可靠性与数据一致性  
6.4 易用性与可访问性  
6.5 兼容性与可移植性  
6.6 可维护性与可扩展性  
6.7 备份、恢复与审计  
6.8 法规、伦理和真实学生数据限制

每条 NFR 应写成“场景—指标—测量条件—验收方式”，避免“界面美观、系统稳定、响应迅速”等不可验证表达。

### 7 需求验证与管理

7.1 验收标准  
7.2 需求追踪矩阵  
7.3 需求评审检查表  
7.4 待定问题  
7.5 需求基线与变更控制

### 附录

A. 完整用例规约  
B. 数据字典  
C. 分析模型与图表  
D. 原型页面索引  
E. 需求来源与访谈记录  
F. 待定问题和决策记录

## 2. 需求编号建议

| 类型 | 格式 | 示例 |
| --- | --- | --- |
| 功能需求 | `FR-模块-序号` | `FR-SCORE-007` |
| 非功能需求 | `NFR-类别-序号` | `NFR-SEC-003` |
| 业务规则 | `BR-模块-序号` | `BR-EXAM-004` |
| 数据需求 | `DR-实体-序号` | `DR-STUDENT-002` |
| 用例 | `UC-模块-序号` | `UC-REVIEW-001` |
| 待定问题 | `Q-序号` | `Q-026` |

需求 ID 一经进入基线不重复使用；删除时标为废弃并保留记录，而不是重编号。

## 3. 单条功能需求模板

| 字段 | 内容 |
| --- | --- |
| ID／名称 | 唯一标识和动宾短语 |
| 描述 | 系统必须提供的外部行为 |
| 来源 | 课件场景、用户访谈、旧需求或评审决策 |
| 优先级 | Must／Should／Could／Won't 或 P0/P1/P2 |
| 参与者 | 获得业务价值或触发交互的外部角色 |
| 前置条件／触发 | 何时执行 |
| 输入与校验 | 业务数据和边界规则 |
| 正常结果 | 可观察的系统响应和状态变化 |
| 异常结果 | 拒绝、提示、回滚或重试 |
| 业务规则 | 引用 `BR-*` |
| 验收标准 | Given/When/Then 或等价的可测试条件 |
| 追踪 | 用例、图、原型、测试用例、后续设计项 |
| 状态 | 草稿／评审中／已批准／已变更／已废弃 |

```text
用例 ID／名称：
目标：
主要参与者：
次要参与者：
前置条件：
触发条件：
后置条件（成功保证／最小保证）：
主事件流：
备选事件流：
异常事件流：
业务规则：
数据与权限：
非功能约束：
验收标准：

```

这个模板保留课件要求的执行者、前置／后置、主流和备选流，并补上权限、验收和追踪，但不采用 SchoolOS 那样每个小功能单独建立几十个文件。

## 5. 非功能需求写法示例（仅示范格式）

不推荐：

> 系统响应速度快，能支持很多学生使用。

推荐格式：

> `NFR-PERF-001` 在约定的课程验收数据规模和单机测试环境下，95% 的学生本人已发布成绩查询请求应在待确认的阈值内返回；测试环境、数据量、并发数和统计方法在测试计划中固定。

阈值暂不写死，需结合课程验收环境与实际压测再确认。

## 6. 追踪矩阵建议

| 需求 ID | 来源 | Actor／用例 | DFD 过程 | 数据实体 | 原型 | 验收／测试 | 状态 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `FR-*` | 访谈／决策 ID | `UC-*` | `P*` | 概念实体 | 页面 ID | `AC-*`／`TC-*` | 草稿等 |

追踪矩阵只记录实际存在的链接，不为了填满表格虚构图、页面或测试。

## 7. 为什么推荐此结构

- 与课件 IEEE 参考结构和旧 V1.0 的老师熟悉骨架兼容。
- 同时覆盖功能、数据、接口、质量属性和验证，而不是只有页面或 CRUD。
- 用少量结构化模型说明边界和数据流，用用例与领域模型说明角色和业务语义。
- 把实现技术放在约束和接口部分，避免 SRS 退化为 Spring Boot/Vue 设计说明。
- 明确待定问题和追踪关系，能支持后续概要设计、数据库设计、API、测试和变更管理。

## 8. 正式写作前的进入条件

1. 补到第一次实验的原始任务与提交要求，确认模板、页数、Word/PDF、图表和 Axure 要求。
2. 评审 `04-业务范围与规则待确认事项.md` 中的最高优先级问题。
3. 冻结 P0 功能、角色与权限边界。
4. 确认图表最小集合和统一符号。
5. 确认是否沿用旧文档封面、签字页和编号格式。

在这些条件满足前，只维护研究稿和大纲，不生成正式 SRS 或 Word/PDF。
